# Codex

Use this reference when Codex is a target host: its reserved names in
Phase 1, and its formats in Mode B. It maps the [team design](../design.md) to
Codex files. Formats were checked on 2026-11-11 against the official
[subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents.md),
[AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md.md),
[advanced configuration](https://learn.chatgpt.com/docs/config-file/config-advanced.md),
[approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security.md),
and [command line](https://learn.chatgpt.com/docs/developer-commands.md?surface=cli)
pages with Codex CLI 0.167.1. The former `developers.openai.com/codex/` URLs
redirect there. Re-read all five pages in every run through their raw `.md` URLs,
only from `learn.chatgpt.com/docs/`, and record what changed; a field or path
the current page no longer documents is not written.

## Files and names

| Item | Path |
|---|---|
| Role file | `.codex/agents/<name>.toml` in the project root, one agent per file |
| Lead block | Root `AGENTS.md`, between the orchestration markers |

- Codex identifies a custom agent by its `name` field; keep the file name
  equal to it.
- **Reserved names:** `default`, `worker`, and `explorer` are built-in agents,
  and a custom agent with the same name replaces the built-in. Do not use
  them; rename in Phase 1.
- **Trusted projects only:** Codex loads project `.codex/` layers, including
  `.codex/agents/`, only when the project is trusted. In an untrusted project
  the lead block can load while the roles do not. Tell the user to trust the
  project through Codex's own prompt or settings; never write a trust entry.
- **Protected directory:** in Codex's workspace-write sandbox, an existing
  `<root>/.codex` directory is read-only. When this skill runs inside Codex,
  writing role files may need an approval the user grants; if it is refused,
  record the write as not done and report it. Never change sandbox settings
  to get around it.
- Global subagent settings live under `[agents]` in Codex configuration.
  `orchestration` never writes `.codex/config.toml`; recommend settings in the
  report instead, such as `agents.max_concurrent_threads_per_session` when the
  design runs many roles in parallel.

## Role file

Write only these keys:

| Key | Value |
|---|---|
| `name` | The role name |
| `description` | The role's description from `docs/agents.md` |
| `developer_instructions` | The complete role specification, as a multi-line string |
| `model` | Only when the design maps the tier to a model verified for this user; otherwise omit to inherit |
| `model_reasoning_effort` | Only together with an explicit `model` that supports the design's effort |

```toml
# Generated by the orchestration skill from docs/agents.md. Change docs/agents.md and materialize again.
name = "reviewer"
description = "Reviews changes for correctness and security against the decisions in docs/stack.md. Use after implementers finish."
developer_instructions = """
<role instructions from docs/agents.md>
"""
```

- `name`, `description`, and `developer_instructions` are required. Codex
  skips, without any message, a file that is not valid TOML, lacks a required
  key, or has an unknown top-level key, so the field check is mandatory.
- Strings: use a basic multi-line string (`"""`), escaping `\` as `\\` and any
  `"""` inside the text. A literal string (`'''`) is valid only when the text
  contains no `'''`. Parse every file before reporting it as written.
- Never write `features.*`, `skills.*`, `sandbox_mode`, `approval_policy`,
  `model_provider`, `mcp_servers`, or other keys. Sandbox, approvals,
  provider, and MCP servers come from the parent session. Feature flags and
  skill toggles do take effect, but they are outside this skill's scope: for
  example, `features.shell_tool = false` removes command execution, which on
  Codex is also how an agent reads and searches files, while file edits stay
  available.

## Capability mapping

| Class | Mechanism on Codex | Enforcement |
|---|---|---|
| read | Command execution and the default tools | Not separable from shell |
| edit | Default patch tool | Not removable per agent: "do not edit" is advisory |
| shell | Command execution | Not removed by this skill: "no shell" is advisory |
| web | Inherited from the parent session | advisory |
| delegate | Codex spawns agents on the lead's request | advisory |

- Codex documents that custom agent instructions can ask an agent to avoid
  edits but do not create a separate read-only sandbox. Record every
  capability restriction and write scope on Codex as advisory, and say so in
  the plan.
- Sandbox and approval settings come from the parent session. Tell the user
  to choose them before asking the lead to delegate.

## Models and effort

- Without `model` in the file, Codex resolves the model and effort from an
  explicit spawn value, then the `[agents]` defaults in the user's
  configuration, then the parent session. Leaving `model` out is the default
  mapping for every tier; the plan says the value is resolved by the host,
  since the skill does not read that configuration, and records the design's
  effort as advisory.
- Map a tier to a model only when a current official Codex page lists it and
  the user confirms access; Codex model names change often, so never copy
  them from an example or from memory. Record the source and date.
- Write `model_reasoning_effort` only with an explicit `model`, using a level
  the current page lists for that model.

## Lead block

- Codex reads instruction files from the project root down to the working
  directory, at most one file per directory, preferring a non-empty
  `AGENTS.override.md`, then `AGENTS.md`, then configured fallback file names,
  and skipping empty files. Creating a root `AGENTS.md` therefore hides a
  fallback instruction file in the root, such as one named in
  `project_doc_fallback_filenames`; before creating it, report any other
  root instruction-like file and state that effect in the plan. Report a
  non-empty `AGENTS.override.md` in the root, since it hides the root
  `AGENTS.md`.
- Codex stops adding instruction files once their combined size, including
  the global file in the user's Codex home, reaches `project_doc_max_bytes`
  (32 KiB by default). Keep the lead block short and report the size of the
  instruction files inside the root; the global file is outside scope.
- Current Codex releases spawn subagents when the user asks or when applicable
  `AGENTS.md` or skill instructions request it; the lead block is that
  instruction.

## Validation

- Parse each file as TOML and check the keys, for example with Python 3.11 or
  later run as `python3 -I`, using `tomllib`: required keys present and
  non-empty strings, no key outside the table above, `name` equal to the file
  name and not reserved. The plan shows the exact command.
- Load check for the user: `codex debug prompt-input`, run in the project
  root, renders the model-visible prompt locally without calling a model, so
  the user can confirm that each role name and the lead block appear. It reads
  the user's own Codex configuration and trust state, which are outside this
  skill's scope, so recommend it in the report instead of running it.

## Starting the team

Report to the user: trust the project in Codex if it is not trusted yet;
optionally confirm loading with `codex debug prompt-input`; start a new Codex
session in the project root; the lead follows the block in
`AGENTS.md`; ask it to delegate to a role by name; in the CLI, `/subagents`
switches between running agent threads.
